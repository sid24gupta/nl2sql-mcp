# Database

The analytics database (`analytics`, PostgreSQL 16) holds synthetic data about how people spend
their working time: which application and screen they used, on which day, for how long, and
whether that time belonged to a defined business process.

The DDL lives in `db/schema.sql`. Table and column `COMMENT`s there repeat the rules below so the
LLM can read them through the schema tools.

## Shape: a star schema

Two fact tables in the middle share the same dimensions around them.

```
                 dim_date
                    |
   dim_team ---- fact_work_daily ---- dim_user
                    |        \
          dim_application   dim_screen

   (fact_process_daily joins to the same dimensions, plus dim_process)
```

- **Fact tables** hold measurements (here: `effort_in_sec`) and foreign keys to dimensions.
- **Dimension tables** hold descriptive attributes you filter and group by (team name, month, ...).

## Grain

The **grain** of a table is what exactly one row represents. Knowing it tells you what a `SUM` or
`COUNT` actually means and when a join will multiply rows.

| Table | Grain (one row per ...) |
|---|---|
| `fact_work_daily` | user, day, application, screen |
| `fact_process_daily` | user, day, application, screen, **process** |
| `dim_date` | calendar day |
| `dim_team`, `dim_user`, `dim_application`, `dim_screen`, `dim_process` | one team / user / app / screen / process |

## Tables

### fact_work_daily
Total effort per user, day, application and screen. Total = process effort + one-off activity.

| Column | Notes |
|---|---|
| `activity_date` | FK to `dim_date.date_key` |
| `user_uuid` | FK to `dim_user` |
| `team_uuid` | FK to `dim_team`. The user's team (always equals `dim_user.team_uuid`) |
| `application_uuid`, `screen_uuid` | FKs to `dim_application`, `dim_screen` |
| `effort_in_sec` | seconds, `>= 0` |

Primary key: `(activity_date, user_uuid, application_uuid, screen_uuid)`.

### fact_process_daily
The process-related **subset** of `fact_work_daily` effort, split per process.

Same columns as `fact_work_daily` plus `process_uuid` (FK to `dim_process`).
Primary key: `(activity_date, user_uuid, application_uuid, screen_uuid, process_uuid)`.

For any user/day/application/screen, the sum of process effort is `<=` the work effort.

### dim_date
One row per day, 2025-10-01 to 2026-12-31 (loaded by `db/dim_date.sql`).
Columns: `date_key`, `day_of_week` (1 = Monday ... 7 = Sunday, ISO), `day_name`, `is_weekend`,
`week_of_year` (ISO week), `month`, `month_name`, `quarter`, `year`.

### dim_team
`team_uuid`, `team_name` (unique).

### dim_user
`user_uuid`, `user_name`, `location`, `role`, `department`, `team_uuid`.
`dim_user.team_uuid` is the user's team, but `dim_user` also lists users with **no activity**,
so don't use it for team analysis (see rule 1).

### dim_application
`application_uuid`, `application_name` (unique), `app_category`
(Development, Communication, Documentation, Browser, ...).

### dim_screen
`screen_uuid`, `screen_name`. A screen has no application of its own: which application a screen
was used in is recorded only on the fact row (`application_uuid` + `screen_uuid`).

### dim_process
`process_uuid`, `process_name` (unique), `team_uuid` = the team that **owns** the process. The owner
can differ from the team of the people who did the work (`fact_process_daily.team_uuid`).

## Golden rules

1. **Team comes from the fact table.** Group, filter and count by `fact.team_uuid`, never by
   `dim_user.team_uuid`. `dim_user` lists every assigned user, including people with no activity;
   the fact tables contain only active users. So team head counts, per-person averages and user
   lists must come from the facts. (Summed effort is the same either way, because inactive users
   have no fact rows.)
2. **Never add work effort and process effort together.** Process effort is already part of work
   effort, so adding them double counts.
3. **One-off activity effort = work effort - process effort**, compared at the same
   user/day/application/screen level.
4. **Filter and display dates through `dim_date`** (weekends, months, quarters, day names).
5. **Use half-open date ranges:** `activity_date >= '2026-09-01' AND activity_date < '2026-10-01'`.
   Never `BETWEEN` on timestamps.

## Access

- The application connects as `nl2sql_readonly` (created by `db/app_user.sql`): SELECT only,
  read-only transactions, 5 s statement timeout.
- **No user-level queries.** `dim_user.user_name` is not readable by the app user, so
  `SELECT *` on `dim_user` fails; select named columns instead. Results must be grouped
  (team, location, role, department, application, screen, process, date), never per user.

## Seeded data

Generated by `db/seed.py` (reproducible: fixed random seed).

- 5 teams, 40 users, 10 applications, 20 screens, 12 processes.
- Facts cover 2025-10-01 to 2026-10-20: about 51k work rows and 36k process rows.
- 4 users are **never active** and 3 users **join late** (first activity Feb to Apr 2026), so
  assigned vs active head counts differ (rule 1).
- Weekdays ~7.5 h per worked day, ~5% leave days; weekends have rare short shifts.
- Process effort is ~35-45% of work effort. Users sometimes perform processes owned by another team.

## Gotchas

- **Effort is in seconds.** Divide by 3600.0 for hours (the `.0` avoids integer division).
- **ISO weeks cross year boundaries.** 2025-12-29 has `week_of_year = 1` (week 1 of 2026) while
  `year = 2025`. When grouping by week, group by the ISO year too, or use date ranges.
- **Process owner vs performer.** "Processes owned by Team Alpha" uses `dim_process.team_uuid`;
  "process work done by Team Alpha" uses `fact_process_daily.team_uuid`.

## Example queries

Hours per team in September 2026:

```sql
SELECT t.team_name,
       ROUND(SUM(f.effort_in_sec) / 3600.0, 1) AS hours
FROM fact_work_daily f
JOIN dim_team t ON t.team_uuid = f.team_uuid
WHERE f.activity_date >= '2026-09-01'
  AND f.activity_date <  '2026-10-01'
GROUP BY t.team_name
ORDER BY hours DESC;
```

Active users per team (from the fact table, not `dim_user`):

```sql
SELECT t.team_name,
       COUNT(DISTINCT f.user_uuid) AS active_users
FROM fact_work_daily f
JOIN dim_team t ON t.team_uuid = f.team_uuid
GROUP BY t.team_name
ORDER BY t.team_name;
```

Process vs one-off hours per team (aggregate each fact separately, then combine):

```sql
WITH work AS (
    SELECT team_uuid, SUM(effort_in_sec) AS work_sec
    FROM fact_work_daily
    GROUP BY team_uuid
), process AS (
    SELECT team_uuid, SUM(effort_in_sec) AS process_sec
    FROM fact_process_daily
    GROUP BY team_uuid
)
SELECT t.team_name,
       ROUND(COALESCE(p.process_sec, 0) / 3600.0, 1)                AS process_hours,
       ROUND((w.work_sec - COALESCE(p.process_sec, 0)) / 3600.0, 1) AS one_off_hours
FROM work w
JOIN dim_team t     ON t.team_uuid = w.team_uuid
LEFT JOIN process p ON p.team_uuid = w.team_uuid
ORDER BY t.team_name;
```

Weekend effort per application:

```sql
SELECT a.application_name,
       ROUND(SUM(f.effort_in_sec) / 3600.0, 1) AS weekend_hours
FROM fact_work_daily f
JOIN dim_date d        ON d.date_key = f.activity_date
JOIN dim_application a ON a.application_uuid = f.application_uuid
WHERE d.is_weekend
GROUP BY a.application_name
ORDER BY weekend_hours DESC;
```
